# Connected pilot accounts

This public registration/login entry uses Supabase Auth internally without requiring a bank sandbox, SMS sender or outbound email service. It creates synthetic `handle@pilot.lumo.invalid` identities for the test-money pilot. The response always declares `contactVerified: false`; no phone, real email or Ghana Card is verified by this flow.

`POST /functions/v1/lumo-pilot-auth/register` accepts exactly `{handle, displayName, password, pin}`. `POST /functions/v1/lumo-pilot-auth/login` accepts exactly `{handle, password}`. Both return a normal Supabase Auth session at the top level plus the current shared account. Errors use `{ok:false,sandbox:true,error:{code,message}}` and an appropriate HTTP status. Session restoration, refresh and logout use the normal Auth endpoints.

The Edge Function uses the runtime's server-only `SUPABASE_SERVICE_ROLE_KEY` to call admin createUser and the restricted bootstrap RPC. The public application never receives that credential. Financial commands still require a real user access token, a live session and the normal server transaction PIN. New regular Auth signups cannot opt themselves into the pilot through editable user metadata.

Registration reserves the handle before creating Auth state. If a response is interrupted, submitting the same registration details again resumes the same synthetic identity. An unused reservation can be released only after a server-side check proves no Auth identity or profile exists. A created identity, opened account or posted financial record is never deleted by this function. An unfinished login directs the tester back to complete registration with the original handle and password.

The bootstrap enforces 15 credential attempts per handle in a 15-minute bucket across both Edge routes, 60 login attempts per ingress-address bucket per 15 minutes, 50 registrations per ingress-address bucket per hour, 500 registration attempts globally per hour, 2,000 total Edge Auth attempts globally per 15 minutes and a 1,000 active/completed registration ceiling. Global limits do not depend on trusting a client-address header. Supabase Auth's own rate limits also apply to direct Auth calls.

Deploy this function with `verify_jwt: false` because registration and password login are public entry operations. This does not disable JWT validation for `lumo_rpc` or expose the service-only bootstrap function. The handler restricts browser CORS to exact configured origins, accepts native requests with no Origin, rejects unknown origins and caps input at 4 KiB. Root deployment must supply the approved website origins; credentials are never allowed through wildcard CORS.

`tests/pilot-auth.test.mjs` covers the HTTP handler with injected transport. `tests/pilot-auth-bootstrap.test.sql` checks grants, trusted metadata, reservations, shared rate limits and safe recovery under the hosted service/user roles, then rolls back all fixtures. Real deployed Auth registration/login, session restoration and cross-channel ledger HTTP requests passed 28 integration checks; see verification/live-pilot-http.json. Browser layout QA uses separate inert display fixtures and does not claim authenticated browser or physical handset execution.
