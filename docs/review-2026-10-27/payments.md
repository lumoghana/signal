# Payments, QR, funding and cards review

Review date: 27 October 2026. Scope: the 43 effective payment-related routes shipped in Everyday, Minna and Hibiscus. The shared source is reviewed here; root owns the rendered browser assessment and edition-specific visual verification. No application source was changed for this audit.

## Method and evidence

Read `AGENTS.md`, the actual script order in `dist/index.html`, the effective view functions and their decorators, then mounted every standard payment-domain route through the retained isolated DOM harness. Forty-one standard routes rendered without fixture errors; `everydayPayments` and `everydayRepeatChoice` were also mounted, bringing the catalogue to 43. Additional mounted checks covered real card reveal/freeze approval, request review/creation, pending/failed/reversed payment results, pristine/filtered Activity, returning bank funding and a card with eight activity records.

The standard `virtualCardAuthorize`, `virtualCardDetails` and `paymentRecovery` fixtures intentionally exercise unavailable/expired fallbacks. Their real approval/recovery paths were assessed through their production entry functions and source, rather than treating the fallback as their complete experience. This audit does not claim browser geometry, camera hardware or real provider verification.

The review used two design passes. Pass one identified first-use comprehension, returning-user speed and recovery issues. Pass two challenged each proposal against existing safeguards and the user's recent decisions. Recommendations below are the changes that survived that challenge. Existing form capture, retained task parents, fresh quotes, explicit approval, pending-result handling, sample boundaries and edition identities remain requirements.

## Second-pass challenges and decisions

1. **Do not count hidden Pay tab panels as visible clutter.** The DOM transcript includes all three panels, but inactive panels carry `hidden` and CSS enforces it. A redesign based on raw text alone would be a false positive.
2. **Do not move optional notes merely to satisfy a form-order convention.** The existing system deliberately folds Add a note below the immediate consequence/review action (`decision-system.js:30`; native styling). This makes the core payment task short. Preserve it unless root browser review finds actual confusion or keyboard trouble.
3. **Do not auto-remember wallet ownership or hide consent/PIN/QR identity notices.** These are decision facts, not repeatable marketing guidance.
4. **Do not remove Recent/Favourites replacement friction.** It protects an unsent draft and rechecks pending payments. The QR path should gain the same quality of confirmation, not weaken the existing path.
5. **Do not change ledger or retry semantics to make outcomes prettier.** Pending money must stay pending, paid-but-undelivered bills must not offer a new payment, and a new failed-payment attempt must have a new reference and fresh review/PIN.
6. **Do not replace paged history with unbounded infinite scrolling solely for novelty.** Existing search/status paging respects the user's small-screen preference. Fix the inaccessible older-card history by using that existing pattern.
7. **Do not hide merchant simulation/role boundaries as “busy text”.** Most provider outcome controls are already test-mode-only. Their source visibility in the harness is not evidence that ordinary customers see all of them.
8. **Do not remove the top-corner QR or move it back to a floating control.** The user explicitly settled the Scan/My code header pattern.

## Suggested implementation packages

1. **State-led payment recovery:** refine ordinary `paymentResult` actions and empty `pending`; preserve the existing controllers. Primary owners: `campus-everyday.js`, `decision-system.js`, `payments.js`. Validate pending/failed/delivery states, reference/idempotency, retained drafts and return routes.
2. **Useful history and search:** correct Activity empty states and pressed semantics; expose complete card history through scoped Activity; give merchant search no-match feedback. Primary owners: `compact.js`, `virtual-cards-ui.js`, `account.js`. Validate long histories, two cards, refunds/holds/failures, no-result searches and no money mutation.
3. **Small interaction consistency:** correct request progress denominator; deduplicate generated recipient context; use explicit card approval labels; extend bank-guide first-use behaviour. Primary owners: `transaction-journey.js`, `focus.js`, `virtual-cards-ui.js`, `page-guidance.js` (existing disclosure integration), with source snapshots/meaningful mounted assertions.
4. **QR retained-draft decision:** replace browser confirmation with the app's bounded Keep/Replace interaction. Primary owner: `personal-qr.js` plus a public native-decision helper or dedicated presentation handler. Validate cancellation preserves old fields, pending/submitted checks re-run, account changes invalidate the choice, camera stops and QR name notice remains.

Root should prioritise the P1 packages and cohesive system styling before optional P2 details. No new financial feature, provider capability, approval shortcut or group mandate redesign is required by these recommendations.
